# UmaKuma conventions memory

- When fixing type-separation consistency, do a domain-level sweep (for example all `src/app/news/*.tsx` files), not one-off files.
- Move component/page `Props` and shared exported types into adjacent `*.types.ts` files and update all imports in the same pass.
- Browse the local dev server at `http://localhost:6400`, never `http://127.0.0.1:6400`: Next 16 blocks cross-origin dev resources for the second host, so the app hydrates no further than its loading state and looks like a data-loading bug.
- Verify game changes for real: `pnpm dev:local` plus `pnpm local:seed` gives a synthetic account (invite code `TEST01`) with trouble and favorite tags already on started items.
- User-facing copy uses Canadian spelling (favourite, colour, centre, catalogue); code identifiers, database columns and API values keep their existing spelling and are never renamed for it.
- Keep every user-facing string in its feature copy module rather than inline, so the eventual i18n layer can swap dictionaries; an `en-US` spelling variant for US members is a future nice-to-have that belongs there.
- Schema changes are not deployed by the pipeline. `prisma/schema.prisma` is applied by hand with `pnpm db:push`; `postinstall` only runs `prisma generate`, which never contacts the database. After any schema edit, push it to production explicitly and confirm with `pnpm db:drift:check` (read-only, exit 2 with the missing SQL). Local verification proves nothing here: a `dev:local` Postgres gets the push while Neon does not, so the feature passes every local test and fails for real users.
- Modals use the shared `ModalShell`; stacking comes from `MODAL_LAYERS`. Hand-rolled `fixed inset-0` overlays drift: of the fourteen that existed, only four locked body scroll, three ignored Escape, and eight omitted `aria-modal`.
- Subject lists render through `SubjectRows` (condensed) and `SubjectCards` (grid) over the shared `SubjectListRow`, with per-surface slots for what genuinely differs. History and the tagged lists are one renderer over two sources.
- Never fetch subject content from the WaniKani API per request: `WkSubjectCatalog` already holds it. `fetchCatalogSubjects` resolves ids from the catalog in one query with the API as fallback. The study queue hydrated related subjects (components, amalgamations, look-alikes — up to 1,957 ids) over sequential API chunks, costing 9-12s of a 15s request; catalog-first took it to ~40ms and warm page loads from ~15s to under 1s.
- `ModalShell` defaults `closeOnBackdrop` to off; informational modals opt in. The risk is asymmetric: a stray click beside a form discards typed input, while an undismissable info panel only costs a click on its close button.
- Never build a sweep regex containing literal `||`: in a pattern that is alternation with an empty branch, so it matches at every position. A `re.sub` with one inflated ten source files to 10-200MB of repeated text. Use plain string replacement for literal rewrites, and assert the file size barely changed before writing.
- The study queue's server cache always holds the whole sorted queue (only unlimited requests write it), so paged requests read it by slicing. Gating reads on `limit === null` meant the request the page actually opens with never hit the cache; opening reads took that call from ~2s to 16ms. Staleness is already covered — review submit, lesson start, tag change and account refresh all clear it, plus a 60s TTL.
- Never key page access on `wkUsername`. An account may have no WaniKani connection at all, so identity is `slug` (permanent, every account has one) with `wkUsername` only as a fallback for links shared before slugs existed. `canViewUserPage` compared usernames and redirected every WaniKani-free member off their own pages — profile included — while their API calls kept working, because `canAccessAccount` matches `joinedByEmail` instead. Route viewer identity through `viewerAddress` in `src/app/shared/viewerAddress.ts` rather than reading `viewerMenuInfo.wkUsername`.
- `pnpm dev` runs against the **production** Neon database. Page loads are read-only and fine; anything that writes (a PATCH route, a save button, a seeding script) must run under `pnpm dev:local` or `node scripts/local-db.mjs run -- ...`, which repoint `DATABASE_URL` at `127.0.0.1:55432`. Scripts that write should refuse a non-local `DATABASE_URL` unless explicitly overridden, as `scripts/seed-test-members.ts` does.
- `pnpm test-members` creates accounts the way Google sign-in does — an email on a row, no WaniKani — and plays real Map runs over HTTP so scores come from real scoring code. Use it to try the site as somebody who is not you; `--remove` cleans up by email domain.
- Check layout with overlays **open**, not just pages loaded. `pnpm test-responsive` loads each page at 393/768/1440 and fails on anything whose box leaves the viewport unless an ancestor scrolls it, then repeats with the study menus open. Two bugs reached production because every check ran at one width with every menu closed: a dropdown right-anchored for desktop ran off the left of a phone, and a grid item's default `min-width: auto` let a wide `<pre>` push a card past the right edge — `minmax(0,1fr)` in an `lg:` template does not protect the implicit column below that breakpoint.
